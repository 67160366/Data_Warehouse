  2) ลำดับการลบและการโหลด
======================================================================
กฎเดียวที่ต้องรักษาไว้คือ ห้ามมีแถวใน fact ที่ชี้ไปหา dimension ที่ไม่มีตัวตน
จากกฎนี้ได้ลำดับที่สลับกันพอดี:

  ลบ   fact ก่อน dimension
       ถ้าลบ dim_customer ก่อน แถวใน fact จะกลายเป็นเด็กกำพร้าทันที

  โหลด dimension ก่อน fact
       ถ้าโหลด fact ก่อน จะไม่มี customer_id ให้ชี้ไปหา

ทำผิดลำดับทั้งสองกรณีจะเจอ FOREIGN KEY constraint failed เหมือนกัน

======================================================================
  3) โหลดข้อมูล
======================================================================
foreign_keys = 1
จำนวนแถวก่อนโหลด : {'dim_customer': 18, 'dim_product': 12, 'dim_time': 120, 'fact_sales': 180}

ล้างของเดิม:
  DELETE FROM fact_sales     180 แถว
  DELETE FROM dim_customer   18 แถว
  DELETE FROM dim_product    12 แถว
  DELETE FROM dim_time       120 แถว

โหลดใหม่:
  to_sql dim_customer   18 แถว
  to_sql dim_product    12 แถว
  to_sql dim_time       120 แถว
  to_sql fact_sales     180 แถว

commit สำเร็จ

  5) ทำไมไม่ใช้ if_exists='replace'
======================================================================
ทดลองในฐานข้อมูลชั่วคราวในหน่วยความจำ ไม่แตะคลังจริง

  schema ที่เราออกแบบไว้:
    name           type      notnull  pk
    customer_id    INTEGER   0        1
    customer_name  TEXT      1        0
    email          TEXT      1        0

  หลังใช้ replace:
    name           type      notnull  pk
    customer_id    INTEGER   0        0
    customer_name  TEXT      0        0
    email          TEXT      0        0

pk หายหมด notnull หายหมด UNIQUE บน email ก็หาย
เพราะ replace ทำงานสามขั้น: DROP TABLE -> CREATE จาก dtype ของ DataFrame -> INSERT
แปลว่างานใน 3A กับ 3B สูญเปล่า และ step 4 ที่จะทดสอบ FK ก็ไม่มีความหมาย

ยังมีปัญหาที่สอง ลองใช้กับตารางที่มี fact อ้างอิงอยู่จริง:
  sqlite3.IntegrityError: FOREIGN KEY constraint failed
  SQLite ปฏิเสธเพราะ fact_sales ยังอ้างอิง dim_customer อยู่
  แปลว่า replace ไม่ใช่แค่ทำ schema หาย แต่รันไม่ผ่านเลย
  (ข้อนี้จะเกิดก็ต่อเมื่อเปิด PRAGMA foreign_keys ไว้ ลืมเปิดเมื่อไหร่
   DROP จะผ่านฉลุยและ schema พังเงียบ ๆ)

คู่ที่ถูกคือ DELETE FROM (ล้างข้อมูลแต่เก็บ schema) + to_sql(if_exists='append')

  7) idempotency
======================================================================
ลองรันสคริปต์นี้อีกรอบ จำนวนแถวต้องเท่าเดิม:
  dim_customer     18 แถว ไม่ใช่ 36
  dim_product      12 แถว ไม่ใช่ 24
  dim_time         120 แถว ไม่ใช่ 240
  fact_sales       180 แถว ไม่ใช่ 360

ถ้าไม่มี DELETE FROM ข้างบน รอบสองจะได้สองเท่า รอบสามสามเท่า และไม่มี error ฟ้อง
